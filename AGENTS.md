# AGENTS.md — MCRITweb (Flask front-end)

MCRITweb is the **browser front-end and user management layer** for [MCRIT](https://github.com/danielplohmann/mcrit) (MinHash-based Code Relationship & Investigation Toolkit). It is a Flask application that renders server-side Jinja2 templates and talks to an **existing** MCRIT backend over its REST API via `McritClient` from the `mcrit` package.

This repository owns **no analysis data of its own**. Families, samples, functions, jobs, and matching results all live in the MCRIT backend; the local SQLite database only holds users, their preferences, and the backend connection settings. For the matching methodology (PicHash/MinHash, LSH banding) see the [mcrit `AGENTS.md`](../mcrit/AGENTS.md).

## Development setup

Requires **Python 3.12 or newer** (`pyproject.toml` sets `requires-python = ">=3.12"`) - inherited from mcrit, which has declared it since v1.10.0 (v1.5.0 to v1.9.x declared 3.11); the reference deployment (`docker-mcrit`) runs **Python 3.12**. Target 3.12 for anything new.

```bash
make init   # pip install -e ".[dev]": the package, plus pytest/pytest-cov/ruff at the versions CI pins
```

`pytest`, `pytest-cov` and `ruff` are not runtime dependencies, so they are not in
`requirements.txt`; `mcrit` declares the first two under its `dev` extra, so they do
not arrive with it either.

A running MCRIT backend (server + worker + MongoDB) is required for essentially every page beyond login/register. Without it, `mcrit_server_required` flashes an error and redirects to the index.

## Common commands

```bash
source ./flask_env.sh     # sets FLASK_APP=mcritweb, FLASK_DEBUG=1
flask init-db             # once, before first use — creates instance/mcritweb.sqlite
flask run                 # http://127.0.0.1:5000/
python -m pytest          # the offline suite, no backend needed
ruff check .              # config in pyproject.toml [tool.ruff]; CI runs exactly this
```

The first browser visit redirects to `/register`; the first registered user automatically becomes `admin` and configures the backend URL/token in the same form.

Optional: set `PROFILER=True` in `instance/config.py` while `FLASK_DEBUG=1` to enable Werkzeug's `ProfilerMiddleware` (output in `instance/profiler/`).

## Architecture primer

- **App factory + blueprints.** `create_app()` builds the app, calls `db.init_app` and `db.migrate`, then registers the six blueprints. There is no ORM and no Flask extension for auth — everything is hand-rolled around `sqlite3` and `flask.session`.
- **One seam for the backend client.** Views call `get_client()` from `views/client.py`; never construct a `McritClient` directly. The no-argument case is cached on `g` for the request, so a page of views reads the server URL and token from SQLite once. Passing kwargs (the API passthrough needs `raw_responses=True` and its own header-derived username) always returns a fresh instance. Tests substitute a backend through the `MCRIT_CLIENT_FACTORY` config key, which is why the seam exists.
- **A failed backend call (#43).** The client answers `None` for a refusal, an unknown id *and* a failure on the backend's side, and most call sites rely on that: a list, a batch lookup (`get_sample_entries`, `dependency_jobs`) or an annotation leaves the missing part out and the page still renders. Leave those on the default client. A call site that cannot carry on without the answer, or that tells the reader "not found" on a `None`, goes through `with_server_errors(client)` from `mcritweb/backend_errors.py`: a failure on the backend's side then raises and becomes a 502 page, so the `None` means only refused or not there. Where the view still cannot carry on, wrap that call in `require_result(..., what)`, which gives a 404 page naming what is missing. A `requests` exception (no connection, a timeout) becomes a 503 page app-wide, and a bare 502 or 504 on `/api`. A broad `except` around a backend call re-raises `BACKEND_FAILURES` first.
- **Request → job → result.** Long-running operations (matching, cross-compare, unique blocks, submissions) return a `job_id`; views redirect to `data.job_by_id` with a `refresh=N` parameter, and the job page polls until the result is ready - not while its tab is hidden, and at once when it is shown again. Result rendering dispatches on the `job_info.parameters` prefix in `data.result()`.
- **Result caching.** Fetched result JSON is written to `instance/cache/results/`, and match diagrams are rendered once to `instance/cache/diagrams/<job_id>[-famid_N|-samid_N|-funid_N][.dark].png` (the `.dark` variant for the dark theme, ADR-0019). Both are keyed by `job_id` and never invalidated for staleness — a changed renderer needs the cache cleared to be visible. Both are written through `write_atomically`, which parks the file in `instance/cache/incomplete/` and renames it into place, so a reader never catches half of one; that third directory is deliberately *beside* the two rather than inside either, because `data.diagram_file` serves every name under `cache/diagrams`. Reports cached before that were written in place, pretty-printed, and a crash could cut one short, so the download streams a cached report unread only when it is compact and ends with the bracket it opens with, and loads any other first (`find_cached_result_filename`): never write a compact report other than through `write_atomically`, which also syncs the file before renaming it. The results directory is bounded, though: `cache_result` evicts the oldest-written reports until it is within `RESULT_CACHE_MAX_BYTES` and `RESULT_CACHE_MAX_FILES` (see below), and an evicted report is fetched again when next viewed. The diagrams directory is not bounded.
- **Filtering happens client-of-backend side.** `MatchingResult.setFilterValues()` / `.applyFilterValues()` (from `mcrit`) are driven by query parameters, falling back to the user's stored `UserFilters` when no filter params are present.

## Key concepts

**The domain vocabulary lives in [`CONTEXT.md`](CONTEXT.md)** — Family, Sample, Function, Query, Job, MinHash, PicHash, Band, Library, the three tokens, roles and operation mode. Read it before naming anything. What follows is the mechanism behind those terms, not their definitions.

- **Role enforcement** — decorators in `authentication.py`: `login_required`, `visitor_required`, `contributor_required`, `admin_required`, plus `token_required` (API) and `multi_user`. `mcrit_server_required` (in `utility.py`) checks backend reachability. Apply the **narrowest** role a route needs, and place the role decorator **before** `mcrit_server_required` so authorization is settled without a backend round-trip. Its probe is cached for `MCRIT_SERVER_PROBE_TTL` seconds; why it is cached rather than removed, and what would have to change before it could be, is [ADR-0012](docs/adr/0012-keep-the-backend-reachability-probe.md).
- **`@bp.route` goes on top, always.** Decorators apply bottom-up, so `bp.route` runs first and registers whatever function is beneath it. An auth decorator written *above* `@bp.route` wraps a name Flask never sees and enforces nothing, while reading exactly like protection — it has happened twice in this codebase. `testRoutePolicy.py` fails on any new occurrence.
  ```python
  @bp.route('/settings')   # first line, outermost
  @login_required          # everything that must run is below it
  def settings():
  ```
- **Where the settings live** — operation mode, both server-side tokens and the backend URL are columns on the single-row `server` table; per-user tokens are `user.apitoken`. `multi_user` blocks registration in single-user mode.
- **Two paginations** — `CursorPagination` (cursor-based, for backend `search_*` endpoints; supports prefixes so several tables can paginate on one page) and `Pagination` (offset-based, for slicing in-memory result lists). Use `CursorPagination` for anything backed by a backend search. Both answer `sort_by` / `is_ascending` / `get_sort_link`, which is all the `sortable_header_col` widget in `table/pagination_widget.html` needs. A `CursorPagination` sends its order to the backend; a `Pagination` sorts the whole list in the view and then slices the page out of it (`sorted_page` in `views/result_sorting.py`) - sorting a page that is already sliced orders one page and leaves the list unsorted.
- **User column settings** — `UserColumnSettings` lets each user pick and order the columns of seven tables. Positions are integers, `-1` meaning "not active".
- **User filters** — `UserFilters` stores the defaults; `MatchingResult.setFilterValues()` / `.applyFilterValues()` apply them.

## Code conventions

- **Python:** 4-space indent. `ruff check .` is configured (`[tool.ruff]` in `pyproject.toml`) and CI runs exactly that; no formatter is configured, deliberately — this codebase has never been formatted and reflowing it would bury the history of every file. Match the surrounding style rather than reformatting; do **not** introduce a repo-wide reformat as a side effect of a change.
- **Templates:** Jinja2 with Bootstrap 5 markup. Put reusable table rows/headers in `templates/table/` as macros and import them; do not copy row markup between pages. To make a *particular* row render differently - a badge on an exact hit, a tinted selection - pass the table macro `row_decorations`, a `{row_id: decoration}` mapping (`templates/table/row_decoration.html`, issue #53), rather than adding another boolean flag to every macro in the chain. Tint and badge colours in a decoration are names resolved against a palette there, never CSS or class names, because row values come from the corpus.
- **Front-end:** no build step, no npm, no bundler. All libraries are vendored under `static/` and included via `url_for('static', ...)` in `base.html`. Do not add a CDN link (deployments are expected to work offline) and do not add a toolchain without being asked.
- **The scripts every page needs load after the first paint, jQuery included** ([ADR-0018](docs/adr/0018-jquery-is-deferred-too.md), [ADR-0021](docs/adr/0021-the-page-scripts-load-after-the-first-paint.md), issue #63): `base.html` queues them with `later(src)` and loads the queue, in order, once the page's first contentful paint is reported - so `$` does not exist while an inline `<script>` runs, nor in a DOMContentLoaded, load or pageshow listener or `window.onload`. Code that runs then and needs jQuery, Bootstrap or any other queued library goes in `whenReady(function () {...})`, which `base.html` defines above every other script - not `$(document).ready(...)` or `$(fn)`, which are themselves calls to `$`. Function declarations stay at the top level of the block, because `onclick=` attributes call them by their global name - and since such a click can come before jQuery has run, read the page without it there where it is incidental (`fetchState` on the pickers); and a control a user reaches first, like the pickers' autofocused search forms, gets its handler bound to `document` while the page parses, not from `whenReady`. A page's own library is queued from `{% block style %}` with `later(...)`, never a `defer` tag - Dropzone too: on the query, submit and import pages `static/dropzone_attach.js`, queued right after it, attaches the zone with the options the template parks in `window.mcritDropzoneOptions` (rewritten from `dropzone.config()`'s `Dropzone.options.myDropzone =`, which would run before Dropzone is there), and the drop overlay fetches it on the first drag; Bootstrap is queued below that block so that it, not jQuery UI, ends up owning `$.fn.tooltip`. `tests/testParseTimeScripts.py` fails on a `$` (or `bootstrap`, `Sortable` and the other names a queued script defines) that runs before the queue has, on a blocking script in `<head>`, and on a plain script that needs jQuery; `tests/testPageAssets.py` fails on a `defer` tag. Code that every page, or a whole family of pages, carries goes in a file under `static/` that the partial queues with `later()`, not inline: the upload form's and the family type-ahead's (`static/upload_form.js`, `static/family_names.js`) were about 10 KB of every page's HTML, which the server page sends uncompressed. A value only the template knows reaches such a file as a `data-` attribute or a global the partial sets; `later()` queues a file once however often a page includes its partial. A new script that every page needs goes into an existing every-page file (`status_message.js`, `post_action.js`, `page_loading.js`), not a file of its own: each file the queue adds cost about 20 to 40 ms of mobile blocking time in Lighthouse.
- **Tables reload by navigating, not by swapping.** A pagination, sort or page-size click is an ordinary link click; `static/page_loading.js` covers the wait with a spinner. Partial rendering was considered and declined in [ADR-0014](docs/adr/0014-no-htmx-for-table-reloads.md) (issue #60) — note in particular that every row-click handler is a direct `$(sel).click(...)` bound once the page is ready (`whenReady`, see above), so replacing a table's markup kills its rows silently. The cross-compare matrix has no row-click handler at all: each score that has matches is an `<a href>` to its report, so a cloned row in a tab filled on first click (issue #182) still works, and only the tooltip handler is delegated from `document`.
- **Colours have names.** Every colour the project paints is a custom property in the `:root` block at the top of `static/style.css`, with its dark value in `static/theme-dark.css` (issue #70, [ADR-0019](docs/adr/0019-dark-theme-on-bootstrap-5-0-2.md)). Use `var(--name)` in templates, CSS and JS; a new colour gets a name in both files (a name only the overrides of vendored widgets need lives in `theme-dark.css` alone). `tests/testTheme.py` fails on a literal colour and on a name only one file defines. Overrides of vendored CSS go into part two of `theme-dark.css`, starting at `:root`. A score tint is `ScoreColorProvider.getMatchTint*`, never a hex.
- **Route naming:** blueprint + snake_case function; always build URLs with `url_for(...)`, never string concatenation.
- **User feedback:** `flash(msg, category=...)` with categories `error` / `warning` / `success` / `info` — `base.html` maps these to Bootstrap alert classes.
- **Request parsing:** use the `parse_*_query_param` / `parse_*_post_param` helpers in `params.py` instead of ad-hoc `request.args.get` + `int()`.
- **Logging:** the codebase uses bare `print()` in several places. Prefer `current_app.logger` for anything new; don't mass-convert existing calls.
- **License:** GPL-3.0-only.

## Web-specific guardrails

- **Autoescaping is your safety net — `|safe` disables it.** Any value crossing into JavaScript uses `{{ value|tojson }}`, which escapes for a script context; `tests/testScriptEscaping.py` fails on a `|safe` anywhere inside a `<script>` block, so there is no exception list to consult. Note that plain autoescaping is *no* substitute there: it is HTML escaping, and a browser does not decode `&#34;` inside script content, so dropping `|safe` produces a mangled literal rather than a safe one. Never pass user- or backend-supplied strings through `|safe` — a family name is chosen by whoever submits or renames a family, and #85 was a real breakout, not a hypothetical one.
- **`|tojson` ends at the script tag, and a JS sink can be further on.** `static/autocomplete.js` builds each type-ahead suggestion as an HTML string and assigns it to `innerHTML`, so a family name that *is* markup executed there even though `|tojson` had delivered it as a perfectly correct JS string. Two sinks in that one string, not one: the button's text, and the `data-label`/`data-value` attributes the same value is interpolated into — an attribute break needs no angle bracket, so escaping only `<`/`>` would look like a fix and not be one. It is vendored and not ours to patch, so family names reach it one way only: `static/family_names.js`, which `templates/js/ac_family_names.html` queues, fetches them from `explore.family_names`, which builds the items with `mcritweb.autocomplete.autocomplete_items` and so HTML-escapes label and value on the way in. The `submit_or_query_dropzone` macro includes that same partial for its family field; no page embeds the names in its source (#192). `tests/testAutocompleteEscaping.py` fails on a `new Autocomplete(`/`setData(` fed anything but an empty literal or the endpoint's `data.suggestions`, and accepts the latter only in that file and only while nothing else there touches it. When a value crosses into JavaScript, ask what the script does with it next — `|tojson` is the transport, not the whole answer.
  - **The escaping costs display, and the cost is real.** The widget finds the lookup in the escaped label and then slices *that* string at the offsets it found (`autocomplete.js:70-77`), so a lookup ending inside an entity severs it: a family named `R&D`, searched for as `R&`, renders as `R&amp;D`. Matching degrades the same way — a lookup containing `&`, `<`, `>`, `"` or `'` no longer substring-matches. Selecting is unaffected; `data-label` still decodes to the original name, so the form posts what it always did. It **cannot** be fixed from the call site: `item.label` (`:110`) is the single value the matcher (`:114`), the highlight index (`:70-72`), the rendered slices (`:75-77`) and the attribute (`:90`) all read, so there is no second field to point at raw text for matching and escaped text for rendering. Fixing it properly means overriding `createItem` from our own script, or replacing the widget — either way, a deliberate change, not a drive-by. `test_the_highlighter_severs_an_entity` pins the current behaviour and tells you when it stops.
- **Every unsafe method needs a CSRF token** — `mcritweb/csrf.py`, a `before_request` check on anything that is not `GET`/`HEAD`/`OPTIONS`/`TRACE`. A new form gets `<input type="hidden" name="csrf_token" value="{{ csrf_token() }}">`; `tests/testCsrf.py` fails on a `method=post` form that does not have one. Scripts read the token from `<meta name="csrf-token">` (`csrfToken()` in `base.html`'s first script) and send it as an `X-CSRFToken` header. Exempt a route only when it does not authenticate by session cookie — `/api` is the one case, since a cross-site request cannot supply its `apitoken` header. The module deliberately mirrors `flask-wtf`'s names so issue #27 can swap it for the real extension without touching a template; see [ADR-0002](docs/adr/0002-hand-rolled-csrf.md).
- **Every script element carries the response's nonce:** `<script nonce="{{ csp_nonce() }}">`. The `Content-Security-Policy` (`SCRIPT_POLICY` in `mcritweb/__init__.py`) runs a script element only with the nonce drawn for that response, plus whatever such a script adds to the page itself (`'strict-dynamic'`), so a file queued with `later()` or fetched by a page's script needs nothing more. An *inline* script that a script creates does need it, which is why `static/live_search.js` gives the scripts of the rows it swaps in the page's nonce (`document.querySelector("script[nonce]").nonce`). `dropzone.config()` writes a script from Python and takes `nonce=csp_nonce()`; a `type="application/json"` data block needs none. `tests/testScriptNonces.py` fails on a template's script without the nonce and on a rendered page's script without that response's; `tests/testContentSecurityPolicyBrowser.py` walks every page in Chromium under the policy. Handler attributes such as `onclick=` still run, under `script-src-attr 'unsafe-inline'`, until they are listeners; a `javascript:` URL does not.
- **A route that writes must be `POST`-only** — `methods=('POST',)`, not a `request.method` check inside a route that also accepts `GET`. A `GET` that writes can be fired by anything that makes a browser fetch a URL: an `<img>` tag, a link scanner, a prefetch. `tests/routePolicy.py` records which routes write and `testRoutePolicy.py` detects a `GET` that writes without saying so. The five `analyze` job submitters are the deliberate exception — navigational URLs that queue a job (issue #97). They are safe to repeat because the **backend already deduplicates**: `QueueRemoteCalls` hashes the method name and parameters into a descriptor and returns the existing job unless `force_recalculation` is set. That only holds if the flag is a real `bool` — forward a raw query string and `"false"` arrives truthy, which forces a fresh job every visit. Parse any such flag with `parse_checkbox_query_param`. Do not copy the `GET`-writes shape itself for anything new.
- **Actions are not links.** For a control that triggers a write, use `<button data-post="{{ url_for(...) }}">` — `static/post_action.js` turns the click into a `POST`. An `<a href>` to a writing route is a bug even if JavaScript intercepts it, because middle-click and prefetch do not run the handler.
- **`SECRET_KEY` is generated and kept in `instance/secret_key`** when the operator has not set one in `instance/config.py` (`mcritweb/secret_key.py`). It used to default to `'dev'`, which let anyone reading this repository sign a session cookie saying `role: admin`. An explicit key still wins, and is still the right answer for a multi-host deployment, where every host must share one.
- **Never log or render secrets:** user API tokens, the server token, password hashes. `ServerInfo.__str__` contains tokens — do not `print` or flash it.
- **The settings page does not print the API token.** Its "Show token" button (`static/show_apitoken.js`) POSTs, with the CSRF token, to `admin.show_apitoken`, which answers the session's own token as JSON and nothing else, `@uncompressed` and `@no_store`; after a regenerate, `SHOW_APITOKEN_NOW` in the session has the page fetch it once on its own. That keeps `/settings` compressed and cacheable: a template that prints a stored secret is sent uncompressed (BREACH) and no-store, and `tests/testCompression.py` fails on one that is not marked, so show a new secret the same way rather than printing it. The script takes the token off the page on `pagehide`, since the page may now be kept in the back/forward cache.
- **`request.remote_addr` is the proxy unless `TRUSTED_PROXY_COUNT` says otherwise.** The reference deployment puts NGINX in front, so the app's only peer is the proxy. `create_app()` wraps `wsgi_app` in Werkzeug's `ProxyFix` when that key is non-zero, taking the Nth `X-Forwarded-For` value **from the right** — the end a trusted proxy appends to. It defaults to `0`: the header is client-written until a trusted proxy has touched it, so trusting it uninvited lets a caller choose their own identity, and a value that is not a hop count (a bool, a float, a count past `MAX_TRUSTED_PROXY_COUNT`) is refused back to `0` rather than guessed at. The count drives `X-Forwarded-For` only — `X-Forwarded-Proto` is replaced rather than appended by a proxy, so it is always read one value deep. Anything that meters, rate-limits or logs per client reads `request.remote_addr` and therefore depends on this being set correctly; do not add a second, ad-hoc way to guess the client address. `tests/testTrustedProxy.py` covers both directions, README documents the setting.
- **Uploads** land in `instance/temp/uploads/`. A query upload (`analyze.query`) is named by the **job id** the backend issued for it, and is written only once that job is queued; `data.submit` does not keep a local copy of submitted binaries. No part of the query upload name may come from the request: naming a `.smda` query by the `sha256` its own report declares let any visitor overwrite another user's stored query, and naming it by a digest of the upload instead makes it unfindable, because promoting a query to a sample (#9) has only the job to go on. `views/utility.query_upload_path` is the single definition of that path, used by both sides. Two ceilings apply and both are config keys, set in `create_app()` and overridable from `instance/config.py`: `MAX_CONTENT_LENGTH` is the app-wide request body limit Werkzeug enforces with a 413 before buffering — generous by necessity, since it applies to every route and `/data/import` takes whole-corpus exports — and `QUERY_UPLOAD_LIMITS` is a `{role: bytes}` mapping checked in `analyze.query` and in the `/api` query routes (`query/binary`, `query/function`), defaulting to 1 MiB for `visitor` and uncapped for any role it does not name (#19). Keep both checks in place when touching the upload paths; `tests/testAppConfig.py` covers them. `analyze.query` checks the cap from the declared `Content-Length` before anything reads the body, which is why the CSRF check takes that route's token from a header only (`CsrfProtect.header_only`, #284): finding it in the form would parse the whole upload first. `/data/submit_or_query` cannot do the same, because it reads its `form_type` field, and with it the body, before it knows the upload is a query; it is contributor-only, and contributors are uncapped by default.
- **The result cache is bounded by two config keys**, set in `create_app()` and overridable from `instance/config.py`: `RESULT_CACHE_MAX_BYTES` (default 1 GiB) and `RESULT_CACHE_MAX_FILES` (default 1000). After every write to `instance/cache/results/`, `trim_result_cache` removes the oldest-written reports until both hold; `None` lifts a bound. `create_app()` validates both the way it does `TRUSTED_PROXY_COUNT` - a non-negative int, a digit string or `None`, anything else a warning and the default - because a non-number would otherwise fail every cache write. A trim that fails is logged and never fails the page. `tests/testResultCacheBounds.py` covers them (#202).
- **The `/api` blueprint is a passthrough, not an API of its own.** When the backend `McritClient` gains a method, extend the router in `api.py` by adding a regex branch — keep paths and parameter names aligned with the backend's REST API rather than inventing new ones. A token carries its owner's role (`g.api_user`), so a branch that writes must also be listed in `CONTRIBUTOR_ONLY` in that module; otherwise the API becomes the cheap way around a role check in the UI.
- **Validate IDs before use.** Route converters use `<int(signed=True):...>` where negative IDs are meaningful (query samples have negative `sample_id`). Check `client.isSampleId` / `isFamilyId` / `isFunctionId` before acting on user-supplied IDs, unless the call you need answers None for an unknown id itself (`getSampleById`, `getFunctionsBySampleId`, `getMatchFunctionVs`): then that None is the check, and a probe first is a second round trip that learns nothing (#207). The client answers None for a backend error too, so the branch that handles it must not assume the id was wrong, unless the call went through `with_server_errors` (see above).

## Database changes

The SQLite schema is versioned by hand — there is no migration framework. Adding or changing a column means touching **all** of:

1. `mcritweb/sql/create_table_*.sql` — the fresh-install schema.
2. The corresponding class in `mcritweb/db.py` (`fromDb` / `fromDict` / `toDict` / `saveToDb`).
3. `db.migrate()` — an idempotent `ALTER TABLE` / `CREATE TABLE` guarded by a check, so existing deployments upgrade on next start.
4. The `CHANGELOG.md` entry, flagging the DB change under **Upgrading** (older entries used `BREAKS DB -> ...`).

Adding a **table column setting** additionally means updating `UserColumnSettings._default_settings`, `create_table_user_column_settings.sql`, and the relevant row/header macros in `templates/table/`. The `sql/` scripts start with `DROP TABLE IF EXISTS` — they are for initialization only and must never be run against a populated database.

## Testing

`python -m pytest` runs the suite with **no backend and no network** — pagination, user filters, the app-factory fixtures in `tests/conftest.py`, and `testMigrations.py`, which upgrades databases built in historical schemas (transcribed from release tags, not read from git — a CI checkout has no tags). `[tool.pytest.ini_options]` in `pyproject.toml` maps the existing `test*.py` naming; keep it rather than renaming to `test_foo.py`. `make test` and `make lint` run exactly what CI runs (`python3 -m pytest`, `python3 -m ruff check .`) — they used to call `nose` and a `.pylintrc` that has never existed in this repository, fixed in v1.4.7.

Three backends are available to tests, all offline. `fake_mcrit` is strict — an unknown method raises `NotImplementedError` naming itself, so gaps surface as actionable failures. `recording_mcrit` never raises, for asking "did this request write anything". `corpus_mcrit` serves real captured reports from `tests/fixtures/` and is what makes result pages renderable; see the README there.

`corpus_mcrit` also implements the **search/cursor protocol** (`_page` in `fixtureData.py`), so `explore.*` can be tested with rows rather than against an empty result set. It models the contract the views depend on — an opaque token, a forward cursor only while results remain, a backward one only off the first page — not mcrit's cursor encoding or its `field:value` query parser; a test needing those needs a real backend. Note that `search_results` values are **dicts**, as they arrive off the wire, and the views must call `.fromDict` on them — as must `id_match` and `sha_match`. That is the client's inconsistency, not a choice of the fake's; see [ADR-0010](docs/adr/0010-search-results-arrive-as-dicts.md) for what `mcrit` would have to change to remove the requirement.

`tests/testBrowser.py` and `tests/testBrowserScoreTooltips.py` are the two modules that
run a browser: they serve the app on a loopback port with `corpus_mcrit` behind it and
drive it with Playwright - the first the unique-blocks page, because the clipboard copy
and the click-to-sort headers are script behaviour that no HTML assertion can reach, the
second the score tooltips of the result pages. `playwright` is not a dependency and CI
does not install it, so both modules skip there — anything CI must keep catching needs
a lint beside it in `testResultPages.py` as well. The pages run under the
Content-Security-Policy, which refuses `eval`, so a `wait_for_function` predicate is
written as a function, `"() => ..."`: Playwright evaluates a bare expression with `eval`
each time it polls, and the wait fails with an EvalError once it has to poll at all.

**Adding a route means adding a row to `tests/routePolicy.py`** — who may call it, and whether it writes. `testRoutePolicy.py` fails on any endpoint in the url_map without one. That table is the record of the current access policy; change a value only together with the code, so it keeps describing reality. Two sets in it, `IN_VIEW_GUARD` and `KNOWN_INERT_DECORATORS`, are ratchets: both are empty today, and both may only shrink. An entry appearing in either is a regression, not a note.

`tests/fixtures/` holds captured backend reports; `tests/fixtures/regenerate.py` rebuilds them against any instance that has one finished job of each type, so they are not tied to one machine. Two trims in it are load-bearing rather than cosmetic — read its module docstring before changing them.

Coverage is thin and nothing exercises a real backend, so for anything touching views or templates still **verify by exercising the app**: `flask run` against a reachable MCRIT backend and walk the affected pages. When changing shared template macros (`table/*.html`), check every page that imports them — a macro is typically used by 3–5 templates. Results are cached under `instance/cache/` and never invalidated for staleness — only evicted for size — so clear it when validating result rendering. `tests/testBrowserScoreTooltips.py` automates part of that walk for the result pages with playwright, and is the place to check anything that only exists once a browser has parsed the page - a `data-hint` tooltip is an attribute, and `hint.css` draws it from `content: attr(data-hint)`, so neither is visible to a test that reads the HTML as text. It **skips** where playwright or its Chromium build is absent, which includes CI today: neither is in `requirements.txt` and CI does not install them, because a browser download on every job of a four-version matrix is not worth it for one page's hover text. Run it locally before shipping a template change.

CI (`.github/workflows/test.yml`) runs `ruff check .` plus the suite on Python 3.12, 3.13 and 3.14 — the last two became reachable only once the Flask 2.2.5 pin was lifted in #27, since it calls `pkgutil.get_loader`, removed in 3.14. There is deliberately **no `ruff format` check** — this codebase has never been formatted and reflowing it would bury the history of every file. Keep `ruff check .` clean; the rule set in `pyproject.toml` mirrors mcrit's.

## Versioning & releases

- The version lives in `pyproject.toml` (`[project].version`) and nowhere else: `get_mcritweb_version()` reads it at runtime from the checkout, falling back to the installed metadata, and `create_app` stores it in `MCRITWEB_VERSION` once. `tests/testPackaging.py` checks that the running version is the declared one.
- `CHANGELOG.md` follows Keep a Changelog. Every PR that changes `mcritweb/` or `pyproject.toml` adds its own entry under `## [Unreleased]` or carries the `no-changelog` label; `.github/workflows/changelog.yml` fails the PR otherwise. An entry that changes the SQLite schema, adds a dependency or changes a default says what an existing deployment has to do, under **Upgrading** — the old entries used `BREAKS DB -> ...` for the schema case.
- A release bumps `pyproject.toml` and renames `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD` in one PR, and once that has merged and CI is green, pushes the `vX.Y.Z` tag. Pushing the tag is the release: `.github/workflows/release.yml` checks the tag against `pyproject.toml` and the changelog, checks that the commit is on `master` and that CI passed on it, builds and installs the wheel, and creates the GitHub release from the changelog section. [`RELEASING.md`](RELEASING.md) describes it and lists what differs from the other MCRIT repositories. **Do not bump the version or push a tag unless explicitly asked.**
- MCRITweb is **deployed from a checkout** — a container image or a local clone — and is not published to PyPI. The release workflow still builds a wheel and installs it, as proof that the package is complete, and attaches it to the GitHub release.
- `mcrit>=1.12.0` is the floor in `pyproject.toml`, mirrored in `requirements.txt`; `tests/testMcritFloor.py` and `tests/testPackaging.py` fail when the two drift. MCRITweb consumes backend data classes (`MatchingResult`, `SampleEntry`, `FunctionEntry`, `UniqueBlocksResult`, …) directly, so a backend release can break rendering; when a fix depends on new backend behavior, raise the floor in both files and say so in the changelog entry. Release order across the ecosystem is in `RELEASING.md`.
- `flask>=3.0` and `werkzeug>=3.0`. The old hard pins at 2.2.5 / 2.3.3 were lifted in issue #27; the lower bounds are there to stop a resolver sliding back to a 2.x that cannot run on Python 3.12+. See ADR-0001 for what was checked.

## Agent guardrails

- **Never** run `git commit`, `git push`, or open a PR unless explicitly instructed.
- **Never** commit anything from `instance/` (SQLite DB, uploads, cached results/diagrams) or an `instance/config.py`.
- **Do not** modify vendored assets under `static/` (Bootstrap, jQuery, DataTables, Dropzone, Font Awesome, SortableJS, `trace_CFG/`, `autocomplete.js`); most carry their own licenses, and `autocomplete.js` carries none at all — its provenance is recorded above instead, which is the only thing standing between it and being edited as if it were ours.
  - **`static/trace_CFG/main_duo.js` is not stock either, it is a project fork.** It already carried our own patches (`// MCRIT resize to minimum of width and height...`, the CSRF headers marked `// mcritweb: issue #83`) before issue #74 added the one hook the comparison page needs, marked `// mcritweb, issue #74`: `showGraph()` records each pane's zoom behaviour in `graph_zooms` and calls `onGraphShown(graph_id)`, which `static/function_compare.js` (project code) implements. Everything else for the synchronised and combined views lives in `function_compare.js`, including `placeCfgTooltip()`, which sizes a block's hover tooltip to its text and keeps it inside its pane and the window for both the side-by-side tooltips (called from `main_duo.js`'s hover handler) and the combined view's. Refreshing `main_duo.js` from upstream would silently drop the hook and re-break the CSRF headers; `tests/testFunctionPages.py::test_main_duo_keeps_the_hook_function_compare_needs` fails when it is gone. `loopify_dagre.js` is untouched. `loopCollapser.js` and `fnManip.js` are not quite, and have not been since they were imported: `loopCollapser.js` creates `g_function` when it is unset, guards against a loop whose parent function is unknown and against a loop without `strippedNodes` (MCRIT's graphs carry no function-parent information), and `fnManip.js` looks up `#xcfg_left` instead of upstream's `#left`. Upstream (hdc-arizona/cfgexplorer) has had no code change since 2018, so there is nothing to refresh from.
  - **The panes were renamed from upstream's `#left`/`#right`**: `#xcfg_left`/`#xcfg_text_right` on the function page, `#xcfg_left`/`#xcfg_right` on the comparison page. Hovering a graph node on the function page scrolls `#xcfg_text_right` by the block's on-screen offset (it is not a positioned element, so `offsetTop` is not relative to it), and `setupTrace()` scrolls the same panel. With hovering working, "Enable Tooltip" shows a block's lines, which come from the analysed binary (API names among them), so they go in as text nodes, not through `innerHTML`. `tests/testFunctionPageHoverBrowser.py` hovers every node in Chromium, `tests/testFunctionPageTooltipBrowser.py` puts markup in an API name and checks the tooltip shows it as text, and `tests/testFunctionVsBrowser.py::test_the_tooltip_stays_inside_its_panel` and `::test_the_combined_tooltip_stays_inside_its_pane` hold the comparison page's tooltips in view.
  - **`static/trace_CFG/main.js` is not stock either.** Besides the CSRF headers marked `// mcritweb: issue #83`, its `getCodefromGraph()` looks up each block's PicBlockHash matches asynchronously and in parallel (`fetchPicBlockMatches`), where upstream sends one synchronous `XMLHttpRequest` per block, which freezes the page and which Chrome reports as deprecated. It draws the code panel in `renderCodefromGraph()` at once, without waiting for the lookups: a block with one starts with a `>>> Matches: looking up...` line, which its answer replaces in place, so the lines below do not move, and which a failed lookup removes; an answer for a graph that `initialize()` has since replaced is dropped. Drawn once every lookup had settled, the code waited for the slowest of them. `main_duo.js` carries the asynchronous lookups in its uncalled copy of the function, still drawn once they all settle. Refreshing either file from upstream brings the synchronous requests back; `tests/testFunctionPages.py::test_the_cfg_scripts_make_no_synchronous_request` fails when they return, and `tests/testFunctionPageCodePanelBrowser.py` holds the lookups back in Chromium and fails when the code waits for them (it skips without playwright, as in CI).
  - **`main.js` also lays a graph out off the page's main thread, and defers the largest (issue #267).** `measureGraph()` sizes the blocks with dagre-d3's renderer on the page, `layOutInWorker()` has `static/trace_CFG/layout_worker.js` lay them out with the same vendored dagre, and `showGraph(isTraceSupplied, laidOut)` draws that layout; without a worker, `showGraph()` lays out on the page as before. Above `CFG_CODE_FIRST_BLOCKS` blocks, `loadWithDotGraphAndFunctionId()` shows the code panel at once and the graph follows when laid out (`drawDeferredGraph()`); above `CFG_DEFERRED_LAYOUT_BLOCKS` it offers a "Draw the graph" button instead (`offerDeferredGraph()`), because drawing a graph that large still takes the main thread; the click runs `findLoopsAndShowGraph()`. `tests/testFunctionPageWorkerBrowser.py` covers the worker. `getCodefromGraph()` builds the code panel once per page, so neither `showGraph()` nor a failed layout sends its block lookups a second time. Any failure to draw a graph, deferred or not, goes through `graphNotDrawn()`, which shows the code and the prompt with the reason and its button. `tests/testFunctionPageDeferredBrowser.py` drives all of this in Chromium (it skips without playwright, as in CI); `tests/testFunctionPages.py::test_the_function_page_carries_the_deferred_graph_prompt`, `::test_a_large_graph_is_offered_rather_than_laid_out_on_load`, `::test_every_failure_to_draw_the_graph_is_reported` and `::test_the_code_panel_is_built_once_per_page` guard the markup and the source in CI.
  - **The comparison page's graphs are laid out in the same worker.** `main_duo.js`'s `layOutGraph()` sizes a graph's blocks on the page and has `layout_worker.js` lay them out, and `showGraph(graph_id, node_colors, laidOut)` draws that layout, as does `function_compare.js`'s `renderCombined(graph, laidOut)` for the combined graph; without a worker, the graph is laid out on the page as before. The combined graph is measured and drawn only while its pane is shown (`onceCombinedShown()`): in a hidden pane it was fitted at `scale(-Infinity)`. `tests/testFunctionVsBrowser.py` covers the worker and `tests/testFunctionPages.py::test_the_comparison_graphs_are_drawn_from_the_worker_s_layout` guards the source in CI.
  - **`static/dropzone.js` is the other exception, and it is load-bearing.** It carries our own patch (marked `START OF PATCH FOR EARLY CONTENT DELIVERY`) that reads the head of the dropped file and exposes it as `file.upload.header` / `header_metadata`, which is what pre-fills the submit form. Stock Dropzone has no such field. Replacing this file from upstream silently disables the pre-fill — `request_filename_info` catches bare `Exception` and returns `{}`, so nothing errors. Note also that `static/dropzone.min.js` is **unpatched**, and flask-dropzone's own `dropzone.load()` macro serves exactly that file: never call `dropzone.load()`. The pages load `static/dropzone-patched.min.js` instead, which `scripts/minify_dropzone.py` writes from `dropzone.js` (comments and whitespace stripped by rjsmin, licence notices kept in its header): change `dropzone.js`, then run the script; `tests/testAssetDiet.py` fails while the two differ.
  - **`static/trace_CFG/lib/dagre-d3.min.js` carries one patch too**, marked `/* mcritweb: the layer graphs`. dagre 0.4.5's `buildLayerGraphs` built one graph per rank with `filterNodes`, each walking the whole layout graph, which was over half of the layout time of a large function (12 of 22 s at 971 blocks); the patch builds them in one pass. `tests/testCfgLayoutBrowser.py` checks that the layout is the one the unpatched line gives and that `filterNodes` no longer walks the graph per rank; refreshing the file from upstream fails both.
- **Do not** change matching or scoring semantics here — MCRITweb only presents what the backend computes. Score→color mappings (`ScoreColorProvider`, `cross_compare.score_to_color`) are presentation and may change; scores themselves may not.
- When work depends on backend behavior, read `../mcrit` rather than guessing at `McritClient`'s surface.
- Clear `instance/cache/` when validating changes to result rendering or diagram generation — otherwise you will be looking at stale output.

## Outward-facing artifacts

Issues, issue comments, PRs — anything carrying the project's name. Filing is hard to un-notify, so the bar is higher than for a local change.

- **Search for duplicates first, and read the near-misses.** Most of this backlog was filed 2022-08 → 2022-11 in a private repository and migrated verbatim, and several items have since had scope silently absorbed by a v1.4.x release. A symptom you just diagnosed is more often a comment on an existing issue than a new issue, and the person who filed it is still waiting. Reading the backlog as if it described today's code will send you to fix what is already fixed.
- **Read the migration footer before trusting a body's age or its issue references.** Every migrated issue ends with `<sub>Migrated from the project's previous, private repository danielplohmann/mcritweb (issue #NN), opened YYYY-MM-DD by …</sub>`, so the GitHub creation date (2026-08-04 for most of the backlog) is the migration date, not the filing date. References *within* those bodies are already safe — they are written as `` `danielplohmann/mcritweb#148` ``, repo-qualified and backticked so GitHub does not autolink them. The footer's own parenthetical is the one trap: it is a bare `#NN`, which GitHub autolinks to whatever live issue now holds that number (#49's footer points at #98, unrelated). Take it as provenance, not as a link.
- **Verify every `file:line` mechanically against the revision you cite** — `git show <rev>:<path> | sed -n '<line>p'` — and name that revision in the comment when the line is load-bearing. A reference written while the working tree carries local edits will be wrong, and wrong line numbers make a reader distrust the whole document. Line numbers also rot: a fix in the same file invalidates them, so prefer naming the symbol and use the line as a pointer, not as the identifier.
- **Tag each claim as measured or inferred**, and give a cheap way to confirm the inferred ones. `tests/` is deliberately offline, so "not reproduced against a real backend" is the normal state for anything past login — say that rather than eliding it. Undifferentiated confidence is how a plausible guess ends up treated as a finding.
- **Say if an implementation already exists** and invite coordination instead of assuming a patch is wanted.
- **Group trivia and low-confidence items into one issue.** Keep separate issues only for things that have to be closed separately.
- **Match the house voice** — read two or three existing issues before writing. The established shape is a short statement of the problem, evidence with `file:line` in backticks, impact, then options or a suggested fix, and no more confidence than the evidence carries.
